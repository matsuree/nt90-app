## 1. 目的

流山市の投票率向上を目指す市民活動「流山投票率90%プロジェクト」の取り組みとして、LINE公式アカウント内で動くミニアプリを提供します。
市民が「投票に行く」と宣言し、投票したら報告します。投票区ごとの盛り上がりをランキングやマップで見える化して、投票へ参加する雰囲気をつくります。

## 2. 基本方針

| # | 方針 | 状態 |
|---|---|---|
| 2.1 | 個人情報の収集は最小限にする。ユーザーを区別できれば十分。LINEのユーザーIDは元に戻せない形に変換して保存し、それ以外の個人情報（表示名・プロフィール画像・年齢・性別・詳しい住所・位置情報）は保存しない | 【決定】 |
| 2.2 | 堅苦しくしすぎない。宣言・報告は自己申告とし、真偽の検証はしない | 【決定】 |

## 3. 用語

| 用語 | 意味 |
|---|---|
| 選挙回 | アプリで扱う選挙の単位。同じ日に行う複数の選挙（例：市長選と市議選）は、まとめて1つの選挙回とする |
| 投票区 | ランキングや集計に使う単位。市の選挙管理委員会が定める投票区（現在は第1〜第46投票区）をそのまま使う |
| 投票所 | 投票区ごとに決められた、投票日当日の投票場所 |
| 宣言 | 「この選挙回で投票に行きます」という意思表示 |
| 投票報告 | 「投票しました」という自己申告 |
| 有権者数 | 投票区ごとの選挙人名簿の登録者数。選挙管理委員会の公表値をもとに、管理者が登録する |

## 5. 選挙回

### 5.1 考え方【決定】

- 選挙ごとに、宣言・投票報告・ランキングなどのデータをひとまとまりで扱う。
- 同じ日に行う複数の選挙は、1つの選挙回にまとめる。

### 5.2 持つ情報

| 項目 | 例 | 状態・備考 |
|---|---|---|
| 名称 | 2027年 流山市長選挙・市議会議員一般選挙 | 【提案】 |
| 投票日 | 2027-04-25 | 【提案】 |
| 対象選挙の内訳 | 市長選挙、市議会議員一般選挙 | 【提案】表示用のテキスト |
| 宣言の受付期間 | 開始：公開した時点<br>終了：投票日前日の23:59 | 【決定】 |
| 投票報告の受付期間 | 開始：期日前投票の初日 0:00<br>終了：投票日の23:59 | 【決定】 |
| 公開状態 | 下書き／公開／終了 | 【提案】下書きはアプリに表示しない |

- 日時はすべて日本時間で扱う。
- 選挙回ごとに管理者が設定する。

### 5.3 期間終了後のルール【決定】

- 受付期間が終わったら、その操作（登録・変更・取り消し）はできない。
- 締め切り後もランキングなどの結果は閲覧できる。

## 6. 投票区

### 6.1 単位【決定】

- 市の**投票区**を集計の単位にする。
- 理由：市は選挙ごとに「投票区別投票結果」（有権者数・投票者数・投票率）を公表している。そのため、分母や公式投票率を組み替えずにそのまま使える。
- 投票区と投票所の一覧は [precincts.md](./precincts.md) にまとめる。

### 6.2 投票区の区域データ【決定】

- 市の投票所一覧と「投票所所在地データ」（緯度・経度、CC BY 4.0）は公開されている。
- **各投票区にどの町名・丁目が含まれるかは、ネット上で公開されていない**（2026-10-27 時点で確認できた範囲）。
- そのため、区域（町名）はデータベースに項目だけ用意し、当面は空欄にしておく（11章の `area_towns`）。
- 手に入ったら登録する。
  - 入手先の候補：流山市選挙管理委員会事務局（04-7150-6100）への問い合わせ
  - 区域データがあれば、町名での検索（6.3）や、マップ・位置情報による提案（6.4）ができるようになる。

### 6.3 投票区の選び方（画面）【提案】

| 方法 | 内容 | 区域データ |
|---|---|---|
| A | 投票所の一覧から選ぶ（「第1投票区　流山北小学校体育館」など）。自宅に届く投票所入場整理券に投票所が書いてあるので、それを見て選んでもらう | 不要 |
| B | 町名で検索して候補を絞る（`area_towns` の文字列から探す） | 必要 |
| C | 位置情報で候補を示す（6.4） | 必要 |

- フェーズ1は A だけで始め、区域データが手に入ったら B を足す。
- `area_towns` が入っている投票区は、投票所名の下に町名を補足表示する。空欄なら何も出さない。
- **保存するのは投票区だけ**。町名は保存しない（2.1）。

### 6.4 位置情報による投票区の提案【提案】（フェーズ3、できればでよい）

1. ユーザーが「現在地から探す」を押したときだけ、端末の位置情報を取得する。
2. 投票区の範囲を表す地図データ（GeoJSON）と照らし合わせて、候補の投票区を示す。
   - この照合は端末の中だけで行う。位置情報はサーバーにも外部サービスにも送らず、保存もしない（2.1）。
3. あくまで提案として表示し、最後はユーザーが確定する。
4. 投票区の範囲の地図データは公開されていないので、自分たちで作る（9.4）。

### 6.5 投票区の持ち方【提案】

- 投票区は、選挙回ごとに持つ（11章の `election_precincts`）。
  - 投票区の分け方や番号は、投票所の新設などで変わることがあるため。
  - 新しい選挙回を作るときは、前回の投票区をコピーし、変更があれば直す。
- 投票区は、選挙回ごとの参加レコード（8章）に保存する。
- 次の選挙回では、前回選んだ投票区を初期値にする。
  - 端末内（localStorage）に投票区番号だけを覚えておく。
  - 投票区の分け方が変わった選挙回では、初期値を使わない。

## 7. ユーザー

### 7.1 識別【決定】

- LINEのユーザーIDだけで識別する。
- LIFFのScopeは `openid` だけにする。表示名やプロフィール画像は使わないため、`profile` は外す。【決定】
  - Scopeが `openid` だけの場合、チャネル同意の簡略化（このチャネルでは常に有効）により同意画面が出ないため、同意画面での友だち追加オプションは表示されない。【決定】
  - 主な入口は公式アカウントのリッチメニューなので、利用者は友だち追加済みとみなし、アプリ内での友だち追加の案内は当面作らない。【決定】
  - リンクの共有機能などで友だち以外の人が開くようになったら、`liff.requestFriendship()` による案内を検討する。`openid` だけでは友だちかどうかを判定できないため、案内は全員に出すことになる。【保留】

### 7.2 本人確認【提案】

- 画面側から送ったIDトークンを、サーバー側（Next.jsのAPI）でLINEのAPIに問い合わせて検証する。
- 検証できたときだけ、ユーザーIDを信頼して使う。画面側から送られたユーザーIDをそのまま信用しない。

### 7.3 ユーザーIDの保存形式【決定】

- LINEのユーザーIDを、秘密鍵付きのハッシュ（HMAC-SHA256）で変換して保存する。
- 元のIDは保存しない。
- 公式アカウントから一人ずつに通知を送る機能は作らない。全員への一斉配信は、公式アカウントの機能で行える。
- 秘密鍵は、Vercelの環境変数にだけ置く。
  - 秘密鍵をなくしたり変えたりすると、過去の記録と同じユーザーだと判定できなくなる。そのため、秘密鍵は安全な場所に控えておく。

## 8. 宣言・投票報告・ランキング

### 8.1 宣言・投票報告のルール【決定】

- 1人につき、1つの選挙回で参加レコードは1件。宣言と投票報告は、このレコードの状態として持つ。
- 状態の変わり方
  - 未参加 →（宣言）→ 宣言済み →（報告）→ 投票済み
  - 取り消しで前の状態に戻る
  - 宣言せずに投票報告だけすることもできる
- 宣言・宣言の取り消しは、宣言の受付期間内だけできる。
- 投票報告・報告の取り消しは、投票報告の受付期間内だけできる。
- 投票区を変えられるのは、宣言の受付期間内だけ。
  - 宣言の締め切り後に投票区を変えられると、宣言ランキングが変わってしまうため。
  - 宣言せずに初めて投票報告する人は、報告するときに投票区を選ぶ。

### 8.2 ランキング【決定】

すべて、投票区の有権者数あたりの割合で並べる。

| # | ランキング | 計算式 | 集計期間 | データ |
|---|---|---|---|---|
| 1 | 宣言率 | 宣言数 ÷ 有権者数 | 宣言の受付期間（投票日前日に締め切り） | アプリで集計 |
| 2 | 投票報告率 | 投票報告数 ÷ 有権者数 | 投票報告の受付期間（期日前投票の初日〜投票日） | アプリで集計 |
| 3 | 投票率（公式） | 選挙管理委員会が公表した投票区別の投票率 | 選挙後 | 管理者が後日登録 |

### 8.3 有権者数の扱い【提案】

- ランキング3（公式投票率）は、市の「投票区別投票結果」の値をそのまま登録する。
- ランキング1・2の分母（有権者数）
  - 当該選挙の有権者数が公表されたら、その値に差し替える。
  - それまでは、直近の選挙の投票区別有権者数で代用する。
  - 投票区の分け方が変わっている場合は、管理者が見積もった値を入れる。

### 8.4 表示の注意【提案】

- アプリの利用者は有権者全体のごく一部なので、宣言率・投票報告率は小さな値（例：0.3%）になりやすい。
  - 小数第2位まで表示し、件数もあわせて表示する。
- 投票区が46あり、一覧にすると長い。
  - 「自分の投票区の順位」を最初に表示する。
  - 一覧は上位から順に並べる。

## 9. ランキング・マップの画面（概要のみ）

- 9.1 ランキングは、選挙回ごとに8.2の3種類をタブで切り替えて表示する。【提案】
- 9.2 集計が終わっていないランキング（例：選挙前の公式投票率）は「集計前」と表示する。【提案】
- 9.3 過去の選挙回のランキングも閲覧できる。【提案】
- 9.4 マップ【決定】
  - 背景の地図
    - Leaflet（地図表示ライブラリ）と国土地理院の「地理院タイル」を使う。無料で、APIキーも不要。
    - 予備として OpenStreetMap のタイルも使える。
  - 投票区の範囲の地図データ（GeoJSON）
    - e-Stat（政府統計の総合窓口）が公開している国勢調査の「小地域（町丁・字）」境界データをもとに作る。
    - 投票区の区域データ（6.2）に従って、町丁・字の範囲をつなぎ合わせる。
    - 町の途中で投票区が分かれる場所（幹線道路で区切るなど）は、おおよその形でよい（2.2）。

## 11. データモデル（案）【提案】

```
elections（選挙回）
  id, name, description, vote_date,
  pledge_start_at, pledge_end_at,      -- 宣言の受付期間
  report_start_at, report_end_at,      -- 投票報告の受付期間
  status (draft | published | closed), created_at

election_precincts（選挙回ごとの投票区）
  id, election_id,
  number（投票区番号）, polling_place_name（投票所名）, polling_place_address,
  area_towns,             -- 区域の町名（テキスト。任意。当面は空欄）
  eligible_voters,        -- 有権者数（ランキング1・2の分母）
  official_turnout,       -- 公式投票率（ランキング3。選挙後に登録する）
  UNIQUE (election_id, number)

participations（参加レコード。宣言・投票報告）
  id, election_id, user_hash, election_precinct_id,
  pledged_at（null = 未宣言）, voted_at（null = 未報告）, updated_at
  UNIQUE (election_id, user_hash)
```

- `user_hash` には、LINEのユーザーIDをHMAC-SHA256で変換した値を入れる（7.3）。
- 書き込みはすべて、サーバー側のAPIでIDトークンを検証し、受付期間を確認してから行う。画面側からSupabaseへ直接書き込ませない。
- ランキングは `participations` を投票区ごとに集計し、`election_precincts.eligible_voters` で割って出す。
